# Agent 开发 · 能力节点内容种子（SkillMap / direction-a）

> 用途：`init --template agent-dev` 由 CLI 读 `templates/agent-dev.md` 生成 `map.json`；本文件是节点教学内容，运行时按 `id` 索引。
> 等级：L0 未接触／L1 能复述／L2 独立应用（apply 在 help_level≤1 下通过）／L3 独立迁移（check 零提示两题都对，≥7 天后复测）。
> 活动：`activity_id = <id>-<stage>`，stage ∈ explain/drill/apply/check；`prereq_gate=1`（可用门槛，先修 ≥L1 即可开始；`mastery_gate=2` 只用于声明先修已独立应用），`target_level` 统一 3。
> 先修：A1←∅，A2←A1，B1←A2，B2←B1，B3←B2，C1←B1，C2←C1,B2，C3←C2,B3，C4←C3，D1←C3，D2←D1,C2，E1←C3,C4。
> 通用评分：通过须有可复现输出；`help_level≥2` 只记 `assisted_completion`，不升等级。

## A1 Python 数据结构与异常（foundation）
- **要点**：`dict` 缺失用 `get`；`except` 要具体；`json` 往返后类型会变。
- **误解**：①`except: pass` 兜住一切 → 改为捕获具体异常；②缺键返回 None → 实际抛 `KeyError`；③报错信息无用 → 需行号与变量。
- **drill**：给 10 行 dict + `json` 代码，指出 3 处会抛异常的地方。
- **apply**：`parse_record.py` 读 `data.json`，缺字段填默认值并打印条数。可接受：`get`、具体异常、失败行号。
- **check**：`json.loads("null")` 返回什么？再取 `["a"]` 会怎样？
- **评分**：说清哪行抛哪种异常＝通过；只加 `except`＝部分。

## A2 HTTP/API 与 JSON 边界（foundation）
- **要点**：状态码分层（2xx/4xx/5xx）；响应体可能不是 JSON；连接与读取是两段超时。
- **误解**：①200 就是成功 → 有些 200 里装着错误对象；②失败一律抛出 → 要分可重试与不可重试；③响应必能解析 → 错误页常是 HTML。
- **drill**：给 4 个响应（200 正常、200 错误体、429、502 HTML），各写一个分支。
- **apply**：`fetch.py` 请求一次，非 2xx 打印状态码与 body 前 80 字。可接受：状态码判断、`HTTPError` 读 `e.read()`、超时设置。
- **check**：连接超时与读取超时分别抛什么异常？怎么分开处理？
- **评分**：四类响应都走到明确分支＝通过；全兜＝部分。

## B1 消息结构与角色（llm）
- **要点**：`messages` 是数组，`role` 决定约束层级；system 放稳定规则，user 放本次数据；模型无状态。
- **误解**：①约束写 user 就够 → 长期规则放 system 更稳；②模型记得上一轮 → 每次都要带上下文；③越长越好 → 冲突指令互相稀释。
- **drill**：把混在一起的“角色+规则+任务+数据”拆成 2 条消息。
- **apply**：`build_messages.py` 输出 JSON 数组：system 固定规则、user 只放数据。可接受：role 正确、约束与数据分离、可序列化。
- **check**：system 说“永远输出 JSON”，user 说“用中文解释”，模型更可能听哪个？
- **评分**：说清哪条放 system 及理由＝通过；只堆消息＝部分。

## B2 结构化输出与解析（llm）
- **要点**：解析失败是常态；先剥代码围栏再 `json.loads`；重试上限 2 次；字段做类型校验。
- **误解**：①模型必返回合法 JSON → 常带围栏与解释；②校验可省 → 类型与必填必须查；③失败就无限重试 → 要有上限与降级。
- **drill**：给 3 段脏输出（带围栏、前后有解释、单引号），写清理函数。
- **apply**：`parse_tool_call.py` 解析→校验→重试→返回 `{ok, data|error}`。可接受：区分三类失败、重试计数、错误带原片段。
- **check**：模型稳定返回 `{"path": 123}`，你报什么错，怎么让它自修？
- **评分**：非法输入不抛未捕获异常＝通过；异常冒泡＝不通过。

## B3 超时/限流/重试（llm）
- **要点**：超时分层设；429 看 `Retry-After`；重试需退避＋上限＋幂等；不可重试的快失败。
- **误解**：①重试总能成功 → 4xx 重试无意义；②一个总超时就够 → 连接与读取分开设；③不必退避 → 会加重限流。
- **drill**：给 3 个场景（超时、429、401），写“重试/不重试 + 退避方式”。
- **apply**：给 `fetch.py` 加重试：最多 2 次、指数退避、记录尝试次数。可接受：错误分类、上限、退避、日志含 attempt。
- **check**：连续 3 次 429 后，用户该看到什么？
- **评分**：重试策略与错误分类一致＝通过；所有错误都重试＝不通过。

## C1 工具 schema 定义（tools）
- **要点**：工具＝名字＋描述＋JSON schema；描述决定模型选不选；3–5 个高区分度工具优于 20 个重叠工具。
- **误解**：①工具越多越强 → 选择歧义与上下文成本；②schema 随便写 → 必填与类型无法校验；③描述可省 → 模型靠它选工具。
- **drill**：给 `read_file`、`calc` 写 schema（含 `required` 与 `description`）。
- **apply**：`tools_schema.json` 定义两个工具，并写 3 条“该选哪个”的依据。可接受：required 齐全、描述含场景、参数无歧义。
- **check**：两个工具描述都写“处理数据”，模型会怎样？怎么改？
- **评分**：schema 可被校验器接受且描述可区分＝通过。

## C2 调用往返（tools）
- **要点**：模型只输出意图（工具名＋参数），执行权在你的代码；结果与错误都要回填成新消息。
- **误解**：①模型会自己执行 → 它没有文件系统权限；②参数错就抛异常 → 回 `{"error": ...}` 更利于自修；③结果不必回填 → 模型不知成败。
- **drill**：画出“用户→模型→dispatch→结果→模型”5 步，标出你写代码的两处。
- **apply**：`dispatch.py` 实现 `dispatch(name, args)`，未知工具与缺参返回错误对象。可接受：白名单、必填校验、错误结构化。
- **check**：模型请求 `calc` 但 `args` 是字符串，你的处理顺序？
- **评分**：分发器不信任模型输入＝通过；直接 `eval` 参数＝不通过。

## C3 Agent 循环与终止（tools）
- **要点**：循环＝观察→决策→执行→回填；必须有步数上限、可判定的终止条件、每步日志；重复同一调用是失败信号。
- **误解**：①跑到做完为止 → 无上限会烧钱或死循环；②模型说完成即完成 → 完成须可验证；③日志事后补 → 每步先写事件。
- **drill**：给一段没有出口的 `while`，写出 3 个停止条件及判定方式。
- **apply**：`agent.py` 最多 5 步，写 `steps.jsonl`，同一工具同参连续 2 次即停。可接受：上限、终止原因字段、日志四字段。
- **check**：第 3 步已达成目标但模型还想调工具，依据什么停？
- **评分**：能从日志复现“为什么停”＝通过；只有 `max_steps` 无原因＝部分。

## C4 错误处理与幂等（tools）
- **要点**：错误四类（输入/配置/远端/逻辑）动作不同；重试要配幂等键；重复提交不得重复计数。
- **误解**：①一把 `except` 兜住 → 配置错误重试无意义；②重试就能过 → 需幂等键＋上限；③写一半中断没关系 → 原子写＋追加日志。
- **drill**：给 5 个报错文本分类并写动作，再为“重复提交”设计幂等键。
- **apply**：给 `agent.py` 加 `sha256(session|activity|answer)` 键与原子写。可接受：分类表、键生成、重复返回旧结果。
- **check**：同一条答案提交两次，第二次应该发生什么？
- **评分**：错误分类与幂等行为都可观察＝通过。

## D1 会话记忆与上下文预算（memory）
- **要点**：上下文有限；保留 system 与最近 2 轮、成对截断、必要时摘要；裁剪要留日志。
- **误解**：①模型能读完整手册 → 先算预算；②按字符随便切 → 按消息/段落切；③摘要总更好 → 关键约束留原文。
- **drill**：给 20 条历史，选出要保留的 6 条并写理由。
- **apply**：`budget.py` 按字符预算裁剪，system 与最近 2 轮不裁。可接受：成对保留、裁剪日志、上限可配置。
- **check**：一次请求报 context too long，你的降级顺序？
- **评分**：裁剪后仍能答对依赖 system 的问题＝通过。

## D2 RAG 边界（memory）
- **要点**：RAG 解决“知识不在模型里/需出处”；失效点：召回为空、召回过期、拼接超预算、忽略引用。
- **误解**：①上了 RAG 就不幻觉 → 无命中照样编，要“无据不答”；②块越小越好 → 丢上下文，须带出处；③检索到就必须用 → 要阈值与降级。
- **drill**：为 30 页手册设计块大小与 ≥3 个元数据字段。
- **apply**：`rag_demo.py` 关键词召回 top-3，无命中走“不知道”分支，答案带出处。可接受：元数据、阈值、拒答话术。
- **check**：用户问手册里没有的内容，输出应该长什么样？
- **评分**：无命中时正确拒答并给下一步＝通过；硬凑答案＝不通过。

## E1 评测集与回归（evaluation）
- **要点**：先定义“什么算对”；指标＝通过率/引用正确率/平均步数/成本；改动后跑同一套用例。
- **误解**：①跑通 demo 就算好 → 固定用例集＋版本；②用例越多越好 → 10 条覆盖边界胜过 100 条重复；③模型自评可信 → 要抽检校准。
- **drill**：为“工具选择”写 5 条用例，含 2 条边界。
- **apply**：`eval.py` 跑 8 条用例，通过率与失败原因写入 `artifacts/eval-report.md`。可接受：输入/期望/判定、失败可归因、含版本日期。
- **check**：改 prompt 后通过率 80%→65%，你怎么定位？
- **评分**：同输入同结果、失败可归因＝通过。
