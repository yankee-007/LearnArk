# LearnArk 公共验收清单（accept-v1）

所有方向面对同一组核心场景；方向特有场景另行追加。
每项结论只能是：`通过` / `失败` / `未测试` / `不适用（须说明理由）`，并附版本、证据路径、复测日期。
研发者不得删测试、放宽阈值或改预期来消除失败。

## A. 核心场景（11 项）

| ID | 验收项 | 必须验证的行为 | 证据要求 | 结论 |
| --- | --- | --- | --- | --- |
| A1 | 初次进入 | 体验者只凭版本公开入口即可开始，无需研发者临时指导 | 体验报告 + 会话记录 + 首个 mentor 开场 | 未测试 |
| A2 | 持续学习 | 依据持久状态定位正确任务和下一步；不重复已完成内容 | `status` 输出 + journal 事件 + 体验报告 | 未测试 |
| A3 | 导师协作 | 切换导师/会话后保留关键状态，不出现互相矛盾的安排 | 切换前/后 handoff 文件 + 两次会话记录 | 未测试 |
| A4 | 教学反馈 | 对预设错误给出针对性反馈，帮助等级可追溯 | 错误答案 + mentor 回复 + help_level 事件 | 未测试 |
| A5 | 能力证据 | AI 代做/看过/跟随完成不被记为独立掌握 | 受助会话 + 能力状态 + 规则测试 | 未测试 |
| A6 | 状态可靠性 | 中断、重复保存、冲突、异常不静默破坏进度 | 可靠性测试输出 + 复现脚本 | 未测试 |
| A7 | 学习者适配 | 三类学习者（基础薄弱 / 能复述不会应用 / 中断返学）与短时约束均有实际体验 | 三份体验报告 | 未测试 |
| A8 | 恢复与同步 | 干净克隆可用；written/committed/pushed 状态准确 | 克隆目录运行记录 + sync 输出 | 未测试 |
| A9 | 跨主题迁移 | 非编程主题完成诊断→活动→反馈→保存的小流程 | 邮件主题项目 + 会话记录 | 未测试 |
| A10 | 独立验收 | 最终版本有新体验者记录；关键问题有独立复测证据 | 新体验者报告 + 复测报告 | 未测试 |
| A11 | 版本独立性 | 各方向可分别启动，数据不串用，差异可观察 | 启动命令 + 独立项目目录 + 比较矩阵 | 未测试 |

## B. 方向特有验收项（各方向自填，至少 3 项）

方向负责人必须在 `design.md` 中定义可检验的异质行为，并在 `acceptance-report.md` 中逐项给出证据。示例：

- SkillMap：能力地图先修关系生效；诊断结果改变首个任务；只有独立应用才提升节点等级。
- Forge：任务/作品驱动；无作品不能通过里程碑；rubric 评分驱动下一步。
- Atelier：导师职责分离；handoff 契约完整；不同导师不重复布置同一任务。
- Tempo：时间预算改变活动选择；到期复习优先；同一天两次短会话不重复同一活动。

## C. 体验与验收分离要求

- 体验者与研发者必须是不同上下文；实现者不得给自己签独立验收。
- 体验报告由体验者本人写，至少包含：方向/版本、任务 ID、体验者标识、场景、实际步骤（含命令）、完成情况、预期与实际差异、证据路径、问题严重度、复现方法、负担（轮数/操作数）。
- 意见与事实分开记录。阻塞问题先留证据，不得悄悄修好后宣称原版本通过。
- 复测必须由另一个真实独立子 Agent 执行，并同时检查相邻流程回归。

## D. 缺陷分级

- **阻塞**：无法开始/继续、覆盖或丢失数据、错误记录完成状态、关键教学判断明显错误。
- **重要**：可继续但明显误导、反复操作、协作不一致。
- **一般**：表达、便利性、次要体验。

每项记录：来源、影响范围、责任人、修复版本、复测证据、状态（打开/已复测关闭/暂缓）。

## E. 三条状态（每个方向分别报告）

1. 工程验收：实现 + 确定性检查。
2. 独立体验验收：真实子 Agent 使用 + 反馈 + 最终新体验者。
3. 外部与真人验证：真实 GitHub / 真实跨设备 / 真人学习效果，分别标注验证或未验证。

## F. 通过条件

- 无未关闭阻塞问题；
- 公共核心场景（A1–A9）实际通过或给出有理由的不适用；
- 重大反馈已处理并由独立 Agent 复测；
- 至少 6 轮有效迭代记录；
- 最终新体验者仅凭入口可完成核心流程。

不满足则该方向标为“未通过验收”，保留版本与证据，不隐藏轮次。
