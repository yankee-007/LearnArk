## 2. 四个方向

| ID | 名称 | 核心假设 | 学习活动如何组织 | 何时介入 | 如何决定下一步 | 主要风险 |
| --- | --- | --- | --- | --- | --- | --- |
| A | **SkillMap 能力地图路径型** | 先建立可诊断的能力地图，学习者更少迷路，返回时更能定位 | 能力节点（含先修）→ 诊断定位 → 讲解/操练/应用/检查四段活动 | 进入新节点、检测到先修缺口、检查失败 | 按“未掌握 + 先修就绪 + 复习到期”排序，取最低层节点 | 地图过细→负担；诊断不准→路径错误 |
| B | **Forge 任务作品驱动型** | 围绕真实作品暴露缺口，比先学后练更有动力、更接近能力 | 里程碑 → 可交付作品 → rubric 评审 → 缺口微课 | 作品提交、卡住超过一轮、评审不通过 | 由当前里程碑与 rubric 缺口决定 | 缺前置知识时挫败；rubric 主观 |
| C | **Atelier 多导师工作室型** | 明确分工的多个导师 + 交接契约能提升连续性与专业度 | planner/concept/coach/examiner/reviewer 五个导师，各自会话 | 进入不同阶段；导师主动交接 | planner 定周计划，当前导师在计划内选活动 | 交接开销大；导师互相推诿 |
| D | **Tempo 动态调度复习型** | 时间预算 + 到期复习 + 低操作负担最适合碎片时间 | 5–20 分钟微活动队列（回忆卡、概念块、代码 kata、讲解回述、小测） | 每次进入按预算调度；到期/薄弱优先 | 打分函数：到期度、薄弱度、目标推进、时间匹配 | 过度碎片化；缺少深度项目 |

**实质区别**（必须在验收中可观察，不只是文案）：

- A 有显式能力地图与先修关系；B 没有课程表，只有里程碑和 rubric；C 有五个职责不同的导师与 handoff 契约；D 有可解释的调度打分与到期队列。
- 四个方向都必须保留多导师、持久记忆、恢复、Git 同步、跨主题，不得以“简化”换取通过。

## 4. 技术路线（共同）

- 本地优先：每个学习目标一个项目目录；`.learnark/` 存状态与事件；`sessions/`、`artifacts/` 存学习记录。
- 状态：追加式 journal（权威）+ 版本化快照（Document，CAS）+ `.bak` 恢复；锁与原子写保证并发安全。
- 导师：方向自有 mentor 协议 + 运行时拼装紧凑上下文（目标、计划、最近事件、薄弱点、交接），调用 LLM；回复末尾机器块 `learn-update`，运行时校验后应用。
- 记忆：能力/薄弱/帮助程度/错因/复习计划/下一步，全部可追溯到事件；自述与观察分级。
- 同步：`learncore.sync`，只提交项目白名单路径，三态报告，不 force push。
- 入口：`python learn.py start`；同时生成 `AGENTS.md`，让 DSH/其他 Agent 能按同一规则代为操作。

## 5. 研发组织

每个方向 4 个真实研发子 Agent（各自独立上下文，产出落盘）：

| 岗位 | 产出 | 验收 |
| --- | --- | --- |
| D-Research 方向负责人/产品研究者 | `design.md`、`version-manifest.json`、方向特有验收项 | 假设可检验、与别方向差异明确 |
| D-Pedagogy 教学与导师设计者 | `mentors/*.md`、`curriculum/*`、导师行为测试 fixture | 诊断/分级提示/记录帮助程度可运行 |
| D-Engineer 实现工程师 | `runtime/learn.py` 及模块、模板、`AGENTS.md` 生成 | 自检命令全绿、E2E 可跑 |
| D-Reliability 记忆与可靠性工程师 | `tests/test_reliability.py`、`doctor`、恢复与同步测试 | 中断/重复/冲突/损坏测试通过 |

体验者、复测者、独立验收者、最终新体验者均为另外创建的真实子 Agent，不进入 16 个研发岗位。

## 6. 轮次计划（每方向）

| 轮 | 重点 | 主证据 |
| --- | --- | --- |
| 1 | 最小完整流程 + 首次使用 | S1 体验报告、阻塞表、基线 |
| 2 | 诊断与教学反馈 | S2 报告、help_level 事件、错误识别复测 |
| 3 | 多导师与持久记忆 | S3 报告、handoff 文件、恢复前后状态对比 |
| 4 | Git 同步与干净克隆 | S4 报告、`git log`、克隆目录运行记录 |
| 5 | 学习者差异与短时 | S5 报告 + P1/P2 差异结论 |
| 6 | 跨主题迁移与阶段验收 | S6 报告、阶段验收记录 |
| 7 | 针对滞留问题修复 + 定向复测 | S7 报告、回归结果 |
| 8 | 深化 + 最终新体验者 | S8 报告、独立验收、比较矩阵 |

每轮必须包含：一个可检验假设 → 实现/场景变更 → 真实独立体验 → 反馈分诊 → 修复 → 独立复测 → 记录。只跑测试或只改文案不算一轮。

## 7. 资源与检查点

- 检查点：设计完成（CP1）、v0.1 可运行（CP2）、每 2 轮（CP3–CP6）、最终验收（CP7）。每个检查点写 `orchestration/checkpoints/`。
- 中断续跑：`RESUME.md` 记录当前轮次、未关闭问题、下一个可执行任务；新主会话据此继续。
- 容量不足时按方向分批，记录真实完成轮次；不把主 Agent 角色扮演算作子 Agent。

## 8. 证据与交付

- 体验报告、修复记录、复测、验收均在 `variants/<id>/experiments/` 与 `evaluation/` 下，可追溯到命令与文件。
- 最终交付：`START_HERE.md`（总入口）、`comparison.md`、`final-report.md`、`trial-script.md`，以及四个可分别启动的版本。
- 外部验证：真实 GitHub 推送与真实跨设备需用户提供仓库/凭据；本机用裸仓库验证 Git 流程，并如实标注。

## 9. 已知限制

- 模拟学习者由同一模型驱动，只能证明系统行为，不证明真人学习收益，也不是严格盲测。
- 时长为对话轮数而非真实学习时长；长期保持与延后复测只能模拟时间，不能冒充真实。
- 单机环境下的“新设备”是干净克隆，不等于真实跨设备验证。
